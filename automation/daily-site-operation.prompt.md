## 最初に行うこと

1. `git status`、現在のブランチ、`origin/main`との差分を確認する。
2. 未コミットの変更がある場合は、ユーザーの作業を混ぜずに更新を中止し、状態だけ報告する。
3. 作業ツリーがきれいな場合だけ `git pull --ff-only` を実行する。
4. README、既存コンテンツ、直近のコミット、本番サイトを確認し、同じ改善を繰り返さない。

## 分析担当: 毎日の数値確認

利用できる場合は、ログイン済みブラウザを使って次を確認する。

- Google Search Console: `https://tabijitakulist.com/` の直近7日間のクリック数、表示回数、CTR、平均掲載順位、上位クエリ、上位ページ
- Cloudflare Web Analytics: `tabijitakulist.com` の直近24時間の訪問数、ページ閲覧数、主要ページ、Core Web Vitals

取得元、対象期間、確定済みの最終日を明記する。前回値が比較可能な場合だけ増減を記す。取得できない場合は推測や古い値の使い回しをせず、「取得不可」と理由を明記する。ガイドからリストへの遷移、生成・保存、商用リンククリック、成果報酬は計測が確認できなければ「計測不可」とする。ログイン、本人確認、APIトークン発行などユーザー本人の操作が必要な場合だけ、最後の報告に必要事項を1件ずつ簡潔に書く。

毎週月曜日は直近28日と前の28日も比較し、季節性とサンプル数に注意して次の順で改善候補を出す。

1. 表示回数が多く、平均順位が11位から30位の検索語とガイド
2. CTRが低く、タイトルと説明文の改善余地があるガイド
3. 実際に閲覧されたガイドからチェックリスト作成へ進みやすくする改善
4. 旅行規定など変わりやすい記述の鮮度と、目的地・季節ページの重複や内部リンク

ページ追加数や更新回数を成果にせず、対象の検索語、ページ、改善理由を日次レポートに残す。

## 戦略担当: 改善方針

分析メモとサイトの状態から、効果が高く安全な改善を0件から3件選ぶ。対象 URL、理由、見送り案、完了条件を実装担当へ渡す。次を優先する。

- 旅行タイプ、季節、同行者、目的地に応じた持ち物リストの実用性
- 入れ忘れを減らすチェック機能、保存、印刷、共有、再訪時の使いやすさ
- スマートフォンの読みやすさ、操作性、アクセシビリティ
- 検索意図に合う文章品質、タイトル、説明、内部リンク、構造化データ
- 表示速度、エラー、壊れたリンク、重複ページの改善

更新するためだけの更新、日付だけの変更、地名だけを替えたページや根拠の弱い大量ページ生成、薄い文章、他サイトの模倣は行わない。変動する旅行情報は公式情報と確認日を示す。十分な改善余地がない日は変更しなくてよい。継続する判断だけ `docs/DECISIONS.md` に残す。

検索実績がある「日数別」「一人旅」「具体的な目的地」の既存ガイドを、新規テーマより優先する。タイトルや説明文は検索語を不自然に繰り返さず、対象者、日数、得られるチェック内容が検索結果で分かるようにする。

## 実装担当とレビュー担当: 実装と公開

1. 既存の設計と実装パターンに合わせて変更する。
2. `npm.cmd run check` と `npm.cmd run build` を実行する。
3. UIを変更した場合は、可能な範囲でPC幅とスマートフォン幅をブラウザ確認する。
4. `git diff --check`、主要導線、内部リンク、canonical、robots.txt、sitemapを確認する。
5. レビュー担当が分析根拠、採用案、差分、検証結果、旅行情報の鮮度、SEOと利用導線を確認する。公開前に修正する指摘が残れば修正・再レビューする。
6. すべて成功しレビューが公開可と判断した場合だけ、内容が分かるコミットを作成して `main` へpushする。
7. Cloudflare Pagesの反映後、`https://tabijitakulist.com/` が正常に表示されることを確認する。

数値確認だけの日はレポートのみ保存し、記録だけを目的としたcommit・pushは行わない。
ローカルに詳細記録を残す場合は `automation/YYYY-MM-DD.local.md` の形式だけを使う。`automation/reports/` やGit管理対象になる場所へ日次記録を作らない。

ドメイン購入、課金、広告契約、個人情報入力、認証情報の変更、CloudflareやGoogleの権限変更、破壊的なGit操作は行わない。
