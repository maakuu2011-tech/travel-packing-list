# 旅じたくリスト 運営基準

## 現状（2026-10-14、リポジトリ確認）

- Astro の静的サイト。条件別チェックリストと13本のガイドがあり、`main` から Cloudflare Pages に公開する日次指示がある。
- canonical、sitemap、robots.txt、OGP、Article・Breadcrumb・FAQ・ItemList 等の構造化データ、関連記事からチェックリストへの導線がある。
- このリポジトリに CI、Search Console / Cloudflare の自動取得、成果イベント計測、広告・アフィリエイトリンクは見当たらない。サービス側の設定や実測値は未確認。
- ガイドの Article 公開日は共通の固定日で、変更日がない記事には同じ固定日を使う。公開日・変更日の正確さは各記事の履歴と照合してから直す。

## 分析と KPI

日次は稼働と異常を確認し、週次に同じ曜日・同じ長さの期間を比較する。Search Console は確定済みの直近28日と前の28日、Cloudflare は同じ28日を基本にする。対象期間、取得日、取得元、検索タイプ、欠測を必ず記す。少数標本の CTR や順位の差を成功と断定しない。

| 段階 | KPI | 判断に使う切り口 |
| --- | --- | --- |
| 発見 | 検索表示、クリック、CTR、平均順位 | クエリ×ページ、目的地、日数、季節、デバイス |
| 利用 | ランディングページ別訪問、ガイド→リスト遷移、リスト生成・保存・印刷・共有 | 流入別、ガイド別。イベント未設定なら「計測不可」 |
| 収益 | 収益対象ページの訪問、商用リンククリック、承認成果数、確定報酬、RPM | 導線別、ページ別。契約・計測未設定なら「計測不可」 |
| 品質 | 主要ページの表示、リンク切れ、Core Web Vitals、問い合わせ | PC・スマートフォン別 |

広告やアフィリエイトの導入前には、まずガイドからリストへ進む利用実績と、どの旅行条件に需要があるかを確認する。収益導線の候補は「利用者がその場で必要とする旅行用品・サービス」に限り、配置、表示、成果の測り方、広告表記、プライバシー方針を決めてから小さく試す。クリックだけを売上とみなさない。

## 旅行サイト固有の判断

- 季節記事は需要の立ち上がり前に確認し、前年同時期とも比べる。季節の違う28日間だけで効果を判定しない。
- 目的地・地域ページは、固有の持ち物や条件があり、公式情報を検証できる場合だけ作る。地名だけ差し替えたページは作らない。
- 既存ガイドの検索意図、重複、関連記事、一覧とトップからの到達性、チェックリストへの導線を先に改善する。
- 旅行条件や規定が変わる記述は一次情報を確認する。確認できない内容は断定せず、公式情報へ案内する。日付だけを更新して鮮度を装わない。
- 構造化データは画面にある内容と一致させる。日付や FAQ を検索結果の表示保証として扱わない。

## 運用の流れ

1. 進行役が Git と本番を確認する。未コミット変更があれば日次の公開作業を止める。
2. 分析担当が数値とコンテンツの状況を短く記録する。取得できない値は欠測にする。
3. 戦略担当が改善を0～3件に絞り、見送り理由と完了条件を決める。
4. 実装担当が採用範囲だけ変更して検証する。
5. レビュー担当が差分と根拠を確認する。公開可の場合だけ進行役が commit・push・本番確認を行う。

日次の詳細レポートは既存どおり Git 管理外の `automation/YYYY-MM-DD.local.md` または実行ログに置く。継続判断のみ `docs/DECISIONS.md` に残し、日次の数値記録だけの commit は作らない。

## 週次 Growth Research（月曜日）

入口は `automation/weekly-growth-research.prompt.md`。Windows の週次タスク `Codex-TabijitakuList-Weekly-Growth` が毎週月曜13:30に起動する。日次の4役はそのまま維持し、週次だけ新しい検索需要を調べる `site_growth_researcher` を戦略判断の前に加える。独立した担当が使える場合も、Growth Research→Strategist→Developer→Reviewer の依存順を守る。

1. Search Console の確定済み直近28日と前28日を比較し、Cloudflare も比較可能な同期間を確認する。
2. 前年同時期データがあれば季節性を確認する。季節が異なる28日比較だけで需要を断定しない。
3. Analyst の観測から **Existing Growth** を抽出する。対象は高表示、順位11～30位、低CTR、順位上昇、実閲覧、チェックリスト遷移、近づく季節需要、情報の鮮度が必要な既存ページ。
4. Growth Research が **New Growth** を最大3件抽出する。対象は未掲載の目的地・日数・季節・同行者・旅行目的・移動手段の検索需要や、旅行前チェック・荷物量計算・忘れ物防止などの機能需要。
5. Strategist が両方を同列で比較し、根拠、期待効果、重複、実装・保守コスト、公式情報の確認可否から採否を決める。
6. 最大1件の新規ガイド・新機能、または既存改善を選ぶ。新規追加なし、変更なしも正常な判断とする。新規ページ数を成果指標にしない。

既存改善70%・新規需要の探索と実験30%を運用目安とするが、実際の優先度は根拠と期待値で決める。週次・月次の確定値は `docs/growth-status.md` に残し、週次記録はサイト変更がない週も週1回まで commit してよい。日次の細かな数値は Git に積まない。少数標本の CTR 変化を成果と断定しない。入国条件、航空会社の持ち込み条件、料金、営業時間、規定は公式情報と確認日を確認する。構造化データは画面と一致させ、Reviewer の公開可判断前に push しない。
