# 運営の意思決定

日々の数値は日次レポートへ記す。ここには継続する方針変更を、根拠・見送り案・再評価条件とともに残す。

## 2026-11-16: 日次・週次運用を Codex アプリ内の同一タスクへ統合

- 決定: 毎日9時の Codex アプリ内自動化で、1分ツールに続けて旅じたくリストを同じチャット内で運営する。旅じたくリストの週次調査は月曜日の同じ実行内で行う。
- 理由: Windows タスクから起動した非対話の Codex CLI は、Codex アプリのログイン済みブラウザへ接続できず、Search Console と Cloudflare の実測値が欠測していたため。同一タスクでは Search Console のログイン済み画面とドメインプロパティ `sc-domain:tabijitakulist.com` を確認できた。
- 停止した経路: `Codex-TabijitakuList-Daily` と `Codex-TabijitakuList-Weekly-Growth` は削除せず無効化した。重複実行を避けるため、通常運用では再有効化しない。
- 原則: Search Console は URL プレフィックスを必須とせず、ドメインプロパティを使用する。Cloudflare を取得できない場合は理由を記録し、推測値や過去値で補わない。
- 再評価: 次の3回の日次実行で、同一チャットの継続、Search Console の取得、Cloudflare の再試行、両リポジトリの分離コミットを確認する。アプリ内自動化が繰り返し失敗し、かつログイン済みブラウザを利用できる代替経路を用意できた場合だけ旧Windowsタスクの再設計を検討する。

## 2026-11-12: 日次運用を実地確認と改善中心へ変更

- 決定: 分析画面を取得できない日も日次運用を止めず、本番の主要導線、既存ガイド、チェックリスト機能、PC・スマートフォン表示を毎日確認する。再現できる問題や明確な品質不足があれば、確認だけで終わらせず実装・検証・公開まで進める。
- 理由: 日次タスク自体は正常に実行されていたが、分析値を取得できない週や少数データの期間に「変更なし」が続き、公開サイトの改善が停滞したため。
- 原則: 更新回数を目的にせず、低品質なページ追加や日付だけの更新はしない。変更なしは、当日の確認対象と見送り理由を具体的に記録できる場合だけ選ぶ。
- 再評価: 4週間後に、確認した導線の範囲、公開した改善、公開後の不具合、検索流入、ガイドからチェックリストへの利用計測状況を確認する。

## 2026-10-15: 週次 Growth Research と成長データ蓄積を追加

- 決定: 日次は既存ページ・チェックリストの改善を中心に継続し、週次に新しい検索需要を探索する Growth Research を加える。
- 理由: 現在の仕組みは既存ガイドの改善には強いが、Search Console にまだ現れていない旅行検索需要を発見しにくい。また、日次ログは Git 管理外なので長期傾向を比較しづらい。
- 運用: Growth Research が最大3候補を提示し、Strategist が Existing Growth と比較して採否を決める。週次・月次の確定値だけ `docs/growth-status.md` に蓄積する。
- 原則: 新規ページ数を成果指標にせず、地名だけを差し替えたページを作らない。既存ガイドと明確に異なる利用価値がある場合だけ新規作成する。既存改善70%・新規需要の探索と実験30%は目安とし、割合自体をKPIにしない。
- 再評価: 4週間後に検索表示、クリック、上位クエリ、新規ガイド流入、チェックリスト遷移、Growth Research 候補の採用率、公開後の品質問題を確認する。未計測の項目は計測不可とする。

## 2026-10-14: 4段階の公開判断を導入

- 決定: 分析→戦略→実装→レビューの成果を順に受け渡す。重大な指摘が残れば公開しない。
- 根拠: 既存の日次指示は数値確認から push までを単一の実行にまとめており、根拠と公開判断の記録が分かれていない。
- 当面の優先: 既存ガイドの検索需要、チェックリストへの利用導線、事実の鮮度を測る。収益導線は需要と利用を確認してから選ぶ。
- 再評価: 4週間後、改善に要した時間、計測できた KPI、公開後の不具合、利用や収益への寄与を見る。
